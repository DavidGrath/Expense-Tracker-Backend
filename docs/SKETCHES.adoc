== Insert Timed Transaction
A transaction's time field is optional, and any time-less transactions are simply appended at the end of the
day for the specific account according to the `sort_key`. For timed transactions, however, some form of ordering should be imposed

* Time-less transactions can be moved around arbitrarily when editing a transaction
* Timed transactions should obey the rules of insertion if they are moved around, meaning it should also prevent the user
from breaking causality on the frontend

=== Variables
* AHasTime
* BHasTime
* XHasTime
* XLessA
* XLessB

* X is the new transaction

The decision table is in link:transaction_time_sequence.csv[]

== Move Around
Sort keys are only really useful if I can perform operations to move them around, so let's discuss that

=== Primitives
* Move up 1 position
** 204 If already at the top, or it's the only item in its sequence
* Move down 1 position
** 204 If already at the bottom, or it's the only item in its sequence
* Move to immediately before X
** 204 If already immediately before X
** Of course, 404 if X doesn't exist
* Move to immediately after X
** 204 If already immediately after X
** Of course, 404 if X doesn't exist
* Move to top
** 204 If already at the top, or it's the only item in its sequence
* Move to bottom
** 204 If already at the bottom, or it's the only item in its sequence

And so these 6 endpoints, if I don't add more, should be supported by all entities with sort keys, except maybe
profiles since I permit just 2. Transactions in particular have extra conditions as highlighted above
