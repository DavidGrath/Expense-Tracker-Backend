== Ordinals, Sort Keys, and Occupancy Slots

* Ordinals: for use with composite foreign keys: these are to avoid the diamond dependency problem, discussed below
* Sort Keys: lexoRank, that's the general idea. I'm using integers instead of strings, but the principle remains the same.
Eventually some rebalancing will need to be done, but it should be so rare that it doesn't cause any major issues
* Occupancy slots: to enforce the constraint: there must be a maximum of `n` children per parent. It works by using a
check constraint on `1 <= occupancy_slot <= n` and a composite unique index as appropriate. Of course, using locking
mechanics like `SELECT... FOR UPDATE` on the parent table on the application side can also help to prevent the
violation of this rule, but I like to lock things into the data model whenever I can. Occupancy slots shouldn't be treated
as an identifier in any way.

=== Diamond Dependency Problem
The problem was present in other tables, but I'll focus on one for this example. This was my original design for sellers:

----
Seller: profileId,...
SellerLocation: sellerId,...
Account: profileId,...
Transaction: accountId,sellerId,sellerLocationId,...
----

The core flaw with this approach is that it allows for multiple paths to the same root entity: profile, from the same
source table: transaction:

[source]
----
Transaction.accountId -> Account.profileId -> Profile.id

Transaction.sellerId -> Seller.profileId -> Profile.id

Transaction.sellerLocationId -> SellerLocation.sellerId -> Seller.profileId -> Profile.id
----

Even though all 3 paths are supposed to agree on the same `profileId`, there's nothing stopping a bug from causing a
divergence from the truth. The solution is to use a composite foreign key, as is the current design:

----
Seller: ordinal,profileId,...
SellerLocation: sellerOrdinal,profileId,...
Account: ordinal: profileId,...
Transaction: accountOrdinal,sellerOrdinal,sellerLocationOrdinal,profileId,...
----

Now `profileId` is present in all the relevant tables
