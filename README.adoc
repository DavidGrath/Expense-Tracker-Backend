== Setting Up Locally

* Have https://dev.mysql.com/downloads/installer/[MySQL 8.0] installed with the executable on your PATH
* https://repo1.maven.org/maven2/org/flywaydb/flyway-commandline/10.22.0/[Flyway 10.22] on your PATH, or symlinked in `/usr/bin`
* Setting up  a user:
[source,mysql-sql]
----
CREATE USER 'expense_tracker' IDENTIFIED BY 'password';
CREATE DATABASE `expense_tracker_database_testlocal`;
CREATE DATABASE `expense_tracker_database_devlocal`;
GRANT ALL ON `expense_tracker_database_testlocal`.* TO 'expense_tracker'@'localhost';
GRANT ALL ON `expense_tracker_database_devlocal`.* TO 'expense_tracker'@'localhost';
----
[source,shell]
----
cd database/flyway
flyway migrate -environment=devlocal
gradlew.bat :app:jooqCodeGenDevLocal
----

=== Naming conventions for constraints
* Primary Keys: `pk_<table_name>`
* Unique Keys: `uq_<table_name>_<column_or_columns>` (Summarize if hitting the 64-character limit)
* Foreign Keys: `fk_<local_table>_<local_column>_<parent_table>`
* Check Constraints: `chk_<table_name>_<column_or_general_name>_<behavior_description>`
* Plain indexes: `idx_<table_name>_<column_names_or_sensible_name>`

== Things to Note

* The project uses an API-first approach, so the endpoints are derived from the link:openapi/openapi.json[OpenAPI specification]
* Generation is done using the codegen plugin with the `openApiGenerate` task
* Any changes to the openapi files should also increment the version number. How exactly to increment it is based on [.line-through]#vibes# discretion
* Subtle issues noted with the plugin:
** Anytime a change is made to `schemas.json`, but not the root `openapi.json`, the Gradle task remains UP-TO-DATE
** Validation doesn't work, likely also because of the file splitting. TODO  I'll try adding a task that does merging and validation before the actual generation
* Concerning repositories:
** Most of the methods should include a parameter that links back to the user: `userId` or `profileId` and the queries should include them, too. Basically https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/IDOR[IDOR] mitigation
* For deadlock prevention, try when possible to acquire locks in sorted order when acquiring multiple locks from the same table

== Testing Guidelines

=== Controller Level

* Create tests classes per ENDPOINT AND VERB, not per controller
** Naming convention: <ControllerName><Verb><SensibleName>Test
* For each test class, the following guidelines should be used where applicable, but they are not the only options, of course:
** Ok test (prefer keeping this specifically as the first in the class)
** ID Not for user
** ID Not for profile
** ID Not exist
** Bad input string
** 204 No content
* In general, when accepting complex objects, try to isolate tests by each field or atomic group of fields
** Latitude and Longitude are an example of an "atomic group" - you don't want one without the other

=== Database Level
* Nontrivial CHECK constraints

== Of Charges and Reductions (Draft)
This relates to the statistics endpoints specifically

A charge is a general term for "additional expense", most notably fees, taxes, and actual charges
Making them all fall under one umbrella is for simplicity's sake.

Charges are included in statistics by default, and the user should have the option to exclude them

Reductions, on the other hand, are any form of item that reduces the income or expenditure of a transaction.
They are therefore considered as a negative amount, even though their value in the database is positive

Reductions are excluded from statistics by default, and the user should have the option to include them.
However, that option will be ignored with the presence of line item filters, explained below. The user
should be notified that option is ignored because of those

=== Line Item Filters
Line item filters include:

* Category
* Person (Pending)
* Event (Pending)

Whenever a line item filter is present, reductions are unconditionally excluded/ignored; reductions are considered as an aspect
of the transaction as a whole
